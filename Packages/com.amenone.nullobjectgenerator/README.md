# Amenone Null Object Generator

interface に属性を付けると、何もしない実装（Null Object）をコンパイル時に生成する Source Generator。クラスに付けると、そのクラスが実装している interface を全部実装した Null Object を生成する。呼ばれた時に Unity のログを出したり、例外を投げたりもできる。

対象は Unity 6（6000.0）以降。Unity 2022.3.62f3 でも読み込めて生成できる事を確かめたが、対象は Unity 6 以降とする。

## 入れ方

Package Manager の「Install package from git URL...」に次を入れる。

```
https://github.com/amenonegames/AmenoneExtension.git?path=/Packages/com.amenone.nullobjectgenerator#nullobjectgenerator/2.0.1
```

入れるだけで、プロジェクトの全アセンブリ（asmdef で分けたアセンブリと、asmdef の無い Assembly-CSharp）でジェネレーターが動く。asmdef に参照を足す必要は無い。

## 使い方

```csharp
using NullObjectGenerator;

namespace Sample
{
    [InterfaceToNullObj]
    public interface IFoo
    {
        int Count { get; }
        void Execute();
    }
}
```

これで同じ名前空間に `IFooAsNullObj` が生成される。

```csharp
IFoo foo = new IFooAsNullObj();
foo.Execute(); // 何もしない
```

クラスに付ける場合:

```csharp
using NullObjectGenerator;

namespace Sample
{
    [InheritsToNullObj]
    public class Player : IMovable, IDamageable
    {
        // 略
    }
}
```

`PlayerAsNullObj` が生成され、`Player` が実装している interface（基底クラスが実装している物も含む）を全部実装する。`Player` の中身は写さない。

ただし、生成される型（名前空間の直下に置かれる）から見えない interface は実装の対象から外す。たとえば、外側のクラスの private の入れ子の interface や、別のアセンブリの internal の interface（参照している DLL の基底クラスが実装している物など）。生成される型はそれらを実装しない。

### ログの指定

属性の引数に `NullObjLog` を渡すと、メンバーが使われた時に次を行う。`[Flags]` なので `|` でまとめられる。

| 値 | 動き |
|---|---|
| `NullObjLog.None`（既定） | 何もしない |
| `NullObjLog.DebugLog` | `UnityEngine.Debug.Log` を出す |
| `NullObjLog.DebugLogErr` | `UnityEngine.Debug.LogError` を出す |
| `NullObjLog.DebugLogWarn` | `UnityEngine.Debug.LogWarning` を出す |
| `NullObjLog.ThrowException` | `System.Exception` を投げる |

メッセージは、getter が `<名前> is null. return default value.`、それ以外（メソッド・setter・イベントの add / remove）が `<名前> is null. do nothing.`。インデクサーの名前は `this[]`。複数の値を指定した時は、Log → LogError → LogWarning → 例外の順に行う。

## 生成される物の例

`[InterfaceToNullObj(NullObjLog.DebugLog)]` を付けた上の `IFoo` からは、次が生成される。

```csharp
// <auto-generated/>
#nullable disable
#pragma warning disable CS0612, CS0618, CS0693, CS1591

namespace Sample
{
    public class IFooAsNullObj : global::Sample.IFoo
    {
        public int Count
        {
            get
            {
                global::UnityEngine.Debug.Log("Count is null. return default value.");
                return default;
            }
        }

        public void Execute()
        {
            global::UnityEngine.Debug.Log("Execute is null. do nothing.");
        }
    }
}
```

- 型の名前は `<元の名前>AsNullObj`。元の型がジェネリックなら、同じ型引数と制約を持つ（`IRepository<TKey, TValue>` → `IRepositoryAsNullObj<TKey, TValue>`）。
- 名前空間は元の型と同じ。入れ子の型でも、外側の型の中ではなく名前空間の直下に作る。外側の型がジェネリックなら、その型引数も持つ（`Outer<T>.IInner` → `IInnerAsNullObj<T>`）。
- アクセス修飾子は、元の型と外側の型が全部 `public` なら `public`、それ以外は `internal`。
- 生成コードの型は全部 `global::` 付きで書くので、`using` や名前の衝突に左右されない。

## 対応しているメンバー

- メソッド（`ref` / `out` / `in` / `params`、既定値つき引数、制約つきのジェネリックなメソッド）。`out` の引数は全部 `default` を入れる。
- プロパティ（get / set / init）、インデクサー、イベント。
- 継承した interface のメンバー、ジェネリックな interface、別アセンブリ（DLL 参照を含む）の interface のメンバー。
- 既定の実装を持つ interface のメンバー（何もしない実装で上書きする）。
- ポインターを使うメンバー（型に `unsafe` を付ける。アセンブリで unsafe を許可しておく必要がある）。

戻り値は次を返す。

| 戻り値の型 | 返す物 |
|---|---|
| `void` | なし |
| `System.Threading.Tasks.Task` | `Task.CompletedTask` |
| `System.Threading.Tasks.Task<T>` | `Task.FromResult<T>(default)` |
| `ValueTask` / `ValueTask<T>` | `default`（完了済み） |
| `Cysharp.Threading.Tasks.UniTask` / `UniTask<T>` | `default`（完了済み） |
| それ以外（値型・参照型・配列・`IEnumerable<T>` など） | `default`（参照型は `null`。空の配列や空の列挙にはしない） |

メンバーは基本的に `public` のメンバーとして書く。次の時は明示的な実装（`void global::Sample.IFoo.Run()` の形）にする。

- 同じシグネチャ（または同じ名前のプロパティとイベント）が複数の interface にある時の、2 つ目から。
- 名前がぶつかる時の、2 つ目から。プロパティ `X` とメソッド `get_X()` / `set_X()`、イベント `E` とメソッド `add_E()` / `remove_E()`、インデクサーとプロパティ `Item` やメソッド `get_Item()` / `set_Item()` など（生成するインデクサーには `IndexerName` を付けないので、名前はいつも `Item`）。
- 生成される型が `public` で、interface か、メンバーのシグネチャ（戻り値・引数・型引数の制約。型引数・配列の要素・タプルの要素の中まで見る）に `public` でない型が含まれる時。`public class C : IA<X>`（`X` が internal）の `IA<X>` のメンバーがこれに当たる。生成される型自体は `public` のまま。
- 型引数を置き換えた結果、メソッドの型引数の制約が C# で書けない形になる時。制約の型が封印したクラス・値型・配列・`object` などになる時（`IA<int>` の `where U : T` が `where U : int` になるなど）と、`class` / `struct` / `unmanaged` の制約と並んでクラスの制約が入る時（`where U : class, T` に `T = System.Exception` が入るなど）。
- `object` のメンバーと同じ形の時（`ToString()`、`GetHashCode()`、`Equals(object)`、`GetType()`、static の `Equals(object, object)` と同じシグネチャのメソッド、`ToString` などと同じ名前のプロパティやイベント）。`public` で書くと、`object` のメンバーを隠す警告（CS0108 / CS0114）になるため。`System.Collections.IEqualityComparer` の `Equals(object, object)` がこれに当たる。

## 対応していない形と診断

次の形があると、その型の Null Object は生成せず、エラーの診断を出す。他の型の生成は続ける。

| ID | 内容 |
|---|---|
| `NOG001` | `ref` / `ref readonly` で返すメソッド・プロパティ・インデクサーがある |
| `NOG002` | static abstract のメンバーがある |
| `NOG003` | 元の型が private / protected の入れ子の型で、名前空間の直下から見えない |
| `NOG004` | 生成される型の名前空間・名前・型引数の数が、別の対象と同じになる（別々の外側の型の中にある同じ名前の入れ子の型など）。重なった対象は全部生成しない |
| `NOG005` | 入れ子のジェネリックな型で、外側の型と同じ名前の型引数がある（`Outer<T>` の中の `IInner<T>`）。生成される型が同じ名前の型引数を 2 つ持つことになるため |

static のメンバー（abstract でない物）、private のメンバー、sealed のメンバーは実装の必要が無いので飛ばす。

次は生成するが、コンパイルエラーになる。

- 生成される型と同じ名前の型を、利用者が同じ名前空間に手書きしている時（CS0101）。生成される型どうしの重なりは `NOG004` で止めるが、手書きの型との重なりはコンパイラのエラーに任せる。
- `UnityEngine` を参照しないアセンブリ（asmdef の `noEngineReferences`）で、`DebugLog` などのログを指定した時。

## アセンブリと生成先

- 生成先は、属性を書いた型と同じアセンブリだけ。アセンブリ A の interface に `[InterfaceToNullObj]` を付けると、`IFooAsNullObj` は A に入る。A を参照するアセンブリからは使え、参照しないアセンブリからは見えない。参照関係は増えない。
- `[InheritsToNullObj]` のクラスがアセンブリ B、interface がアセンブリ A にあってもよい。生成物は B に入る。
- 属性と `NullObjLog` は、各アセンブリに internal で生成する。そのため `InternalsVisibleTo` でつないだアセンブリでは、相手の internal の属性も見え、属性を使った所で警告 CS0436（型が衝突しているので、自分のアセンブリの方を使う）が出る。動きには影響しない。消したい時は、その所を `#pragma warning disable CS0436` で囲む。生成した属性のファイルの中では、この警告を止めてある。
- この警告は、属性に `Microsoft.CodeAnalysis.EmbeddedAttribute` を付ければ消せる（Roslyn 4.3 と Unity 6000.7 で確かめた）。ただし Roslyn 4.3 には、その属性を安全に足す API（`AddEmbeddedAttributeDefinition`、4.14 以降）が無く、自分で定義することになる。このジェネレーターは全アセンブリで動くので、他のジェネレーターが同じ型を別の形で出すアセンブリがあると、そこでエラーになる。そのため警告の方を残している。

## 元の版からの移り方

1. 元の DLL（`NullObjectGeneratorForNewerThan2022.2.dll`）をプロジェクトから外す。`com.amenone.vcontainerextensions` 0.1.x に同梱されていたので、0.2.0 以降へ上げる。両方あると、属性が二重に定義されてエラーになる。
2. このパッケージを入れる。属性・`NullObjLog`・生成される型の名前・名前空間は元と同じなので、使う側のコードは変えなくてよい。
3. 元の版では DLL を置いた asmdef（とそれを参照するアセンブリ）でしか動かなかったが、この版は全アセンブリで動く。asmdef の参照で範囲を絞っていた場合も、その参照は不要になる。

動きが変わる所:

- 元の版では属性の引数の `NullObjLog` が効いていなかった（いつも `None` 扱い）。この版では効くので、`ThrowException` などを書いていた所は、呼ばれると例外を投げるようになる。
- `Task` / `Task<T>` を返すメンバーが `null` ではなく完了済みの Task を返す。
- 生成される型の名前は同じだが、hintName（生成ファイルの名前）は `Sample.IFoo.AsNullObj.0b591636.g.cs` の形に変わった。末尾の 8 桁は型の完全名から決まる値で、大文字小文字だけが違う型（`IFoo` と `Ifoo`）でもファイル名がぶつからないようにするため。
- 生成される型にコンストラクターを書かなくなった。引数なしの `public` のコンストラクターが暗黙に付く（元は型と同じアクセス修飾子のコンストラクター）。

## 確かめた事と確かめていない事

確かめた事:

- `Source~` のテスト（xUnit。生成結果を C# 9 でコンパイルしてエラー・警告が無い事、生成物を読み込んで呼んだ時の戻り値・ログ・例外、別アセンブリの interface、明示的な実装になる条件、見えない interface を外す事、診断、hintName、増分のキャッシュ。1 つの型の編集、空白・コメントだけの編集、名前が重なる型の追加・削除で、関係ない型の出力が作り直されない事）。
- Unity 6000.7.0b1 で、asmdef で分けた互いに参照の無い複数のアセンブリと Assembly-CSharp の全部でジェネレーターが動く事。生成物が属性を書いた型のアセンブリに入り、参照するアセンブリから使え、参照しないアセンブリからはコンパイルエラーになる事。interface と `[InheritsToNullObj]` のクラスが別アセンブリで、`UniTask` を返すメソッドを含む形。`InternalsVisibleTo` でつないだアセンブリで CS0436 が属性を使った所にだけ出る事。
- Unity 2022.3.62f3 でも DLL を読み込み、警告やエラーを出さずに生成する事（対象外の版で、結果としてそうなっているだけ。今後も保つとは限らない）。

確かめていない事:

- Unity 6000.0〜6000.6 の各版。
- git URL での入れ方（埋め込みパッケージとしてだけ確かめた）。
- IL2CPP でのビルドと実機での動き。
- 大きなプロジェクトでのコンパイル時間の計測。

## ジェネレーターのビルド

ソースは `Source~` にある（Unity は読み込まない）。`Source~/NullObjectGenerator` で `dotnet build -c Release` を実行すると、ビルドした DLL が `Analyzers/NullObjectGenerator.dll` に写される。テストは `Source~` で `dotnet test NullObjectGenerator.sln`。

ビルドは決定的にしてある（`Deterministic`、`PathMap`、Source Link と git の情報を入れない設定）。同じソースなら、置き場所が違っても同じ DLL になる。ただしコンパイラーの版が変わると DLL も変わるので、`Source~/global.json` で .NET SDK 10.0.115 を指定している（同じパッチの帯の新しい版にだけ進む）。`Source~/.gitattributes` で改行を LF に固定しているのも、同じ理由（改行が変わると DLL と生成する属性のファイルが変わる）。
